## 3. 版の準備(T0)

### 3.1 版の箇所

1つのコミットで、次を0.9.1に上げた(`../RELEASING.md`の手順2)。packages/*のbranch-aliasは`0.9.x-dev`のままである。

- `Kernel::VERSION`を`0.9.1`にした。
- packages/*・starters/*・examples/sample-siteのcomposer.jsonの`tmswp/*`の制約(`require`と`require-dev`)を`^0.9`から`^0.9.1`にした(PATCHが0より大きい版の形)。
- examples/sample-siteのpathリポジトリの`versions`(6つ)を`0.9.1`にした。
- 版の例(packages/*/README.mdの要件の行、examples/sample-site/README.md、docs/01・02・08・11)を0.9.1と`^0.9.1`にした。docs/10には、版の例として今の版を示す箇所が無かった。
- tests/Unit/PackageManifestTest.phpの`testComposerManifestsMatchThePackageTableOfDocs01`は、docs/01 §3.1の表の`^X.Y`を`^<MAJOR>.<MINOR>`の文字列に置き換えて照合していたため、制約が`^0.9.1`になると失敗した。今の版の制約を`Kernel::VERSION`から求める補助(`currentConstraint()`。PATCHが0なら`^X.Y`、0より大きければ`^X.Y.Z`で、リリースの前の検査の`requiredConstraint()`と同じ規則)を足し、このテストと`testExtensionManifestFollowsCommonConvention`の制約の照合を、その補助との完全一致にそろえた。docs/01 §3.1の表の下の説明にも、PATCHが0より大きい版では`^X.Y.Z`であることを書いた。
- tests/Unit/PackageManifestTest.phpとdocs/01 §3.1の表の下の説明は、T0の対象ファイル領域に無いが、パッチの版の制約(`^X.Y.Z`)を初めて使ったことで直す必要が生じたため、版の引き上げと同じ変更で直した。
- 版の上げ方を、リリースのときに道具が書き換える、またはリリースのたびに更新するとしていた古い記述を、今の運用(版の最初のタスクで手で上げ、リリースの道具は書き換えず、リリースの前の検査がタグの版との一致を確かめる)に直した。直したのは、docs/11 §8.2のスターターのcomposer.jsonの説明(`tmswp/core`の制約)、docs/02の`Kernel`のコードの写しのdocblockと§3.9の`Kernel::VERSION`の項、packages/core/src/Kernel/Kernel.phpの`VERSION`のdocblockである。
- CHANGELOG.mdの先頭(説明文の後、`## v0.9.0 — 導入できる版`の前)に`## Unreleased`の節を開き、版の引き上げを「変更」に書いた。

### 5.3 起動の確認(`--no-dev`の`vendor/`と`WP_DEBUG`の無効)

`tools/lib/isolated-wp-env.sh`で隔離したwp-env(作業ディレクトリはセッションの一時ディレクトリの下、ポート8893。ルートのwp-env(8888)とexamples/sample-siteのwp-env(8882)には触れていない)で確かめた。WordPressはルートの`.wp-env.json`と同じ`core`(最新の版)の7.1.4、PHPは8.3.36、WP-CLIは2.12.0、`@wordpress/env`は12.0.0である。wp-envの設定で`WP_DEBUG`を`false`にした。

1. `tools/ci/create-starter-project.sh theme <ディレクトリ>/deploy-check deploy-check 'Deploy Check'`でテーマを作った(tmswp/core 0.9.1)。rest.mdの完全な実装例を、名前空間だけを`DeployCheck\Hook`に変えて`app/Hook/PostApiHook.php`に置き、テーマの`composer lint`・`composer analyse`・`composer test`が成功した。
2. スターターの`bin/setup.php`は探索結果ファイルを消すため、隔離したwp-envで一時的に`WP_DEBUG`を真にして`wp tmswp discover`を実行し(開発環境での作り直しに当たる)、書かれた`tmswp-discovery.php`をテーマに置いた。`PostApiHook::registerRoutes`(`rest_api_init`)と例のブロックが入っている。その後、`WP_DEBUG`を偽に戻した。
3. deploy.mdの手順のとおり`composer install --no-dev --optimize-autoloader`を実行した。`vendor/`は`autoload.php`・`composer/`・`psr/`・`tmswp/`だけで、`composer show tmswp/core`は`versions : * 0.9.1`だった。
4. deploy.mdの「上げるもの・上げないもの」のとおりに、上げないもの(`node_modules/`・`blocks/`・`tests/`・開発の設定ファイル・`AGENTS.md`・`README.md`)を除いた写しを作り、それをテーマとしてwp-envに割り当てた。
5. `WP_DEBUG`が偽のWordPressで、テーマを有効にして起動できた。
   - `wp eval`: `WP_DEBUG=false`、Kernelのdebugは`false`、`Kernel::VERSION`は`0.9.1`。
   - トップページは200で、`critical error`・`Fatal`・`Warning`・`Notice`・`Deprecated`の文字列を含まない。管理画面(ログインした管理者)も200。
   - 例のブロック`deploy-check/example`が登録されている。`wp tmswp discover --check`は`Success: discovery files are up to date for 1 kernel(s)`。
6. 保守モード: `wp maintenance-mode activate`の後、トップページは503。保守モードの間も`wp tmswp discover --check`は成功し、`wp tmswp migrate --dry-run`は`Warning: No models registered.`で終わった(Modelを置いていないため)。保守モードの間にもう一度`activate`すると`Error: Maintenance mode already activated.`になり、`activate --force`は`.maintenance`の時刻を書き直した。`deactivate`の後は200。WordPressが`.maintenance`を10分で無効とみなすこと(`wp_is_maintenance_mode()`)と、`wp_maintenance()`がプラグインの読み込みより前に呼ばれること(`wp-settings.php`)は、WordPress 7.0のソースで確かめた。
7. 版の食い違い: スターターのプラグインを、pathリポジトリの版を0.9.2にしたcreate-projectで作って`--no-dev`の`vendor/`を入れ、その`vendor/tmswp/core`の`Kernel::VERSION`を`0.9.2`に書き換えて、0.9.2で作ったプラグインに見立てた(探索結果ファイルは、テーマを外した状態で`wp tmswp discover`で作った)。テーマ(0.9.1)と一緒に有効にすると、トップページ・管理画面・RESTが500になり、ログには`KernelException: tmswp/core versions on this site do not match the loaded core 0.9.2: 0.9.1 at .../themes/deploy-check/vendor/composer/../tmswp/core`が出た。`wp eval`も同じ例外で止まった。`wp --skip-plugins --skip-themes maintenance-mode activate`・`status`・`deactivate`は動いた。プラグインを外すと200に戻った。テーマだけが有効な状態で`wp plugin activate`すると、同じ例外で有効化に失敗し、プラグインは有効にならなかった。探索結果ファイルの無いプラグインを有効にした状態では、すべての要求と`wp`のコマンドが`DiscoveryException: discovery file not found`で止まった。
8. OPcache: wp-envのWebのコンテナのPHPは`opcache.validate_timestamps=1`・`opcache.revalidate_freq=2`だった。`wp config set`で`wp-config.php`の`WP_DEBUG`を変えた直後の要求は古い値で動き、3秒待った後の要求は新しい値で動いた。deploy.mdの「OPcache」の記述(更新を確かめる間隔)に合う。

WordPressの挙動を、確認用のmu-pluginで登録したルートでも確かめた。

- `args`に`type`と`maximum`だけを書いた引数(`validate_callback`も`sanitize_callback`も無い): `n=9`・`n=abc`とも400。`sanitize_callback`の既定(`rest_parse_request_arg`)の中で検証される。
- 同じ引数に`'sanitize_callback' => 'sanitize_text_field'`を足したもの: `n=9`・`n=abc`とも200で、値がそのまま渡った(検証されない)。
- さらに`'validate_callback' => 'rest_validate_request_arg'`を足したもの: 400。
- `permission_callback`を省いたルート: 200で誰でも呼べ、`register_rest_route`の`_doing_it_wrong()`(`The REST API route definition for t1check/v1/no-permission is missing the required permission_callback argument. ...`)が出た。
- 処理のメソッドが例外を投げるルート: `Accept`を付けない`curl`の要求には、500で、JSONでない「There has been a critical error on this website.」の画面が返った。JSONを受け付ける要求(`wp_is_json_request()`が真)にはコード`internal_server_error`のJSONの500が返ることは、WordPress 7.0の`wp_die()`のソースで確かめた(実環境では確かめていない)。

実装例の最初の版では、`permission_callback`(`canEditPost()`)が検証の後の整数を前提に例外を投げており、ログインしない要求で`excerpt`を201文字にすると500の画面になった。WordPressの`rest_send_allow_header()`(`rest_post_dispatch`のフィルタ)が、`Allow`ヘッダを作るために、検証に失敗した要求でもそのルートのすべての`permission_callback`を検証の前の値で呼ぶためである。`permission_callback`で型を確かめて例外を投げない形に直し、rest.mdの「権限の判定」にこの挙動を書いた。直した後は、上の表のとおり400になった。

### 5.5 計画の記述との差

### 6.4 スターターのログの出力先(b)

選んだ方法: スターターの`tests/bootstrap.php`で、`WP_CONTENT_DIR`をシステムの一時ディレクトリの下の、プロジェクトごとのディレクトリに定義する。

- `tmswp-kernel.php`には手を入れない。本番では、WordPressが定義する`WP_CONTENT_DIR`の下(`wp-content/tmswp-logs/`)にこれまでどおり書く。テーマ・プラグインのディレクトリの中には書かない。
- `tmswp-kernel.php`に、定数の有無で出力先を切り替える分岐は作らない。ユニットテストの側で、WordPressが定義する定数を用意する形である。
- `tmswp-kernel.php`で出力先を明示する案は採らなかった。テーマ・プラグインの位置から`wp-content`を推測する書き方は、テーマ・プラグインを`wp-content`の外に置く構成で誤り、`WP_CONTENT_DIR`を使って明示しても、ユニットテストに定数が無いことは変わらないためである。
- `SimpleLogger`の新しい引数等の公開APIは要らなかった。v0.9.1の後の機能の候補に移すものは無い。
- ユニットテストだけで定数を定義するため、本番と違う経路が1つできる。`app/`のコードが`WP_CONTENT_DIR`を直接読んでも、ユニットテストでは検出されない。このため、packages/testing/rules/testing.mdとスターターのAGENTS.mdに、`app/`のコードからこの定数を直接読まない規則を書いた。
- 利用者は、作ったプロジェクトのユニットテストで、そのまま`KernelConfig::load()`で`tmswp-kernel.php`を読み、`logChannels`を呼べる(`TmswpKernelTest`が手本)。ログを書くテスト(`wp_hash()`等をBrain Monkeyで差し替えた場合)は、一時ディレクトリの下に書く。

直す前の再現: 作ったテーマ・プラグインの`tests/bootstrap.php`から`define()`の行を消して`TmswpKernelTest`を実行すると、どちらも`TMSWP\Core\Exception\InvalidArgumentException: SimpleLogger requires WP_CONTENT_DIR when dir is omitted`のエラーになった(確かめた後に元に戻した)。
