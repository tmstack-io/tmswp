## 3. 実装内容の要約

- ConnectionとQueryBuilder(T2)
  - Connectionの`insert`・`update`・`delete`の値をR3で正規化し、NULLを代入できるようにした。テーブル名はベア名だけを受け付ける。QueryBuilderの`update`でもNULLを代入できる。
  - `value()`・`pluck()`は既存のSELECT句を保ち、結果に無いキーと不正なpluckのキーを例外にする。grouped countはORDER BY・LIMIT・OFFSETを捨てる。
  - プレースホルダは`%d`・`%f`・`%s`・`%i`・`%%`だけを受け付け、`%%%s`と番号付きを拒否する。値が無いときは`%%`を`%`に戻す。
  - whereInのlistでない配列、Closureのグループの中のalias、JOINのベア名でないテーブル名、PHPのintの範囲外の値を例外にした。ハイドレーションで欠けたカラムにはコンストラクタの既定値を使い、intのenumを文字列の値から変換する。
- テンプレート前処理(T1)
  - ActionRouter・View・NotFound・`tms_var()`・NoOutputRule・NoSet404Rule・tms-checkと、そのテスト・設定・fixtureを削除し、`KernelConfig`の`actions`の引数を削除した。
  - rules/actions.mdを削除し、明示呼び出し方式のレシピrules/page.mdを新設した。sample-siteのpage-contact.phpを`ContactPage::handle()`の形にした。
  - docs/00・01・02・04・07・10・11・README、スターターとsample-siteのAGENTS.md・composer.jsonを明示呼び出し方式に合わせた。
- Template(T5)
  - includeするクロージャをどのクラスにも束縛せず、テンプレートからTemplateのprivateと`$this`に触れられないようにした。テンプレートから見える変数は`$args`だけにした。
  - `Template::part()`は、slugを検証した後に`get_template_part_{$slug}`と`get_template_part`をWordPressの`get_template_part()`と同じ引数・順序で発火し、その後にテンプレートを解決する。
  - `TemplateLocator::addFallbackDir()`は、空になるパスで`InvalidArgumentException`を投げる。
- ModelファサードとTableDefinitionとPHPStan拡張(T3)
  - `rowClass()`の既定をnull(行はstdClass)にし、`find()`・`first()`が行を返す。Modelのコンストラクタを引数なしの`final public`にし、QueryBuilderのコンストラクタと`as()`はModelのクラスを行のクラスとして拒否する。
  - `update`・`delete`・`count`をdocs/06のシグネチャに合わせ、`useConnection()`を全Modelに共通にしてnullで解除できるようにし、`table()`をキャッシュする。どのKernelにも属さないModelは、`useConnection()`を案内する例外にする。
  - TableDefinitionで、予約語のカラム名・インデックス名と、charsetの無いcollationを宣言時に例外にする。
  - `Model::query()`や`new QueryBuilder`から始まるチェーンの`get`・`first`・`Model::find`の行の型を、`as()`か`rowClass()`の宣言型で絞るPHPStan拡張を足した。
- Emailルールの国際化ドメイン名(`08a3593`)
  - docs/05の同梱ルールの一覧のEmailの行に、国際化ドメイン名とローカル部の非ASCIIは違反、punycodeのドメインは合格と書いた。FormRuleTestにこの3つのケースを足した。
- Migrator(T4)
  - テーブルの作成と変更を、起動時の自動適用から`wp tmswp migrate`(`--dry-run`・`--force`)に移した。結果の`action`はenumのMigrationAction(Migrated・Skipped)。公開の`migrate()`を削除した。
  - 未適用のテーブルがあれば、`manage_options`の権限を持つ利用者にだけ管理画面で通知する。`Migrator::listen()`による通知とCLIの登録は、Migrator・Connectionを解決せず、`$wpdb`を必要としない。
  - dbDeltaの後に、lastError(検証1)、dbDeltaの残りの差分(検証2)、`SHOW FULL COLUMNS`・`SHOW TABLE STATUS`で読んだ実際の構造(検証3)を定義と照らし合わせ、食い違えば`MigrationException`にしてハッシュを更新しない。
  - TableDefinitionの組込の列は、NULLの可否・既定値・既定値の種類を型の付いた属性で持つ。`rawColumn()`では、型の別名と、dbDeltaが収束しない表記を宣言時に`SchemaException`にする。
  - ハッシュの読み書きの失敗をWpDatabaseGuardで検出して例外にする。Kernelのフックのメソッドの失敗のログの文脈を、許可したキーだけにした。CLIの出力の文を翻訳の対象にし、日本語訳を足した。
- Modelのテストとレシピ(T6)
  - `Connection::prepare()`の結果を`remove_placeholder_escape()`に通して返す(A4-L06)。
  - WpdbTestDoubleの`prepare()`をWordPress 7.1の`wpdb::prepare()`の手順に合わせ、実wpdbと代役に同じ入力を通して比べるWpdbTestDoubleParityTestを足した。
  - ModelIntegrationTestに、空でない表の`find`・`first`・`get`、DateTime・enum・NULLの保存、`%%`を含むSQL、grouped count、`value`・`pluck`、攻撃的な値の8つの終端メソッドでの扱い、設計の利用例のテストを足した。
  - FormIntegrationTestのJtiStoreのDBエラーのテストを、乱数の種を固定して決定的にした(srcは変えていない)。
  - rules/model.mdを書き直した(`wp tmswp migrate`の使い方、`MigrationException`の直し方、拒否する型の表記、rowClassとuseConnection、value・pluck・count、固定ページを器に独自テーブルの詳細を出すときの404の扱い)。
- T6の完了条件を満たすための追加のタスク(`4a0a658`)
  - TableDefinitionAcceptanceTest・QueryBuilderAcceptanceTestを新設し、docs/06のTableDefinitionとQueryBuilderの受け入れ基準(不正なスキーマ・誤用の例外、`whereNotIn`の空、Closureのグループのbindingsの順、DTOの日時の厳密な解析、欠落したカラム等)を直接確かめるテストを足した。
  - raw断片の`literal-string`を、PHPStanのコマンドを子プロセスで実行して確かめるPHPStanRawFragmentLiteralStringTestを足した。
  - ModelIntegrationTestに、空の`insert([])`のSQLと、プラグインの有効化・ajax・cron・フロントエンド(`template_redirect`まで)の経路でマイグレーションしないことのテストと、Migratorが登録するコールバックが`admin_notices`だけであることを確かめる構造のテストを足した。
  - ViewTest・ViewIntegrationTestに、解決のキャッシュ(`is_file`の回数)、不正なslugの全種類、例外のメッセージの候補のパス、テーマの同名ファイルによるプラグインのテンプレートの上書き、複数のフォールバックの登録順のテストを足した。LayerConventionTestの対象にModelとViewを加えた。
  - `TableDefinition::toSql()`の索引の行を、docs/06 §2のとおりPRIMARY KEY → UNIQUE KEY → KEYの順に出すようにした(今まではUNIQUEとKEYを宣言の順に混ぜていた)。
  - DTOの日時の変換で、NULを含む値を`createFromFormat()`の前に`HydrationException`にした(今まではValueErrorがそのまま出ていた)。
  - docs/06の品質ゲートに例外(`QueryException`と`MigrateCommand::__invoke`)を書き、docs/06のグループの括弧の表記(`(a OR b)`)と、docs/07 §1.3のパスの区切り(`DIRECTORY_SEPARATOR`)を実装に合わせた。

### 5.4 wp-envでの`wp tmswp migrate`の実行

T4の検証コマンドとdocs/06の受け入れ基準(「`wp tmswp migrate` / `--force` / `--dry-run`が§6の出力どおり動作する(ユニットテストとwp-envでの実行)」)のうち、wp-envでの実行を本書の確認時に行った(T6から持ち越した)。開発用サイトではTMSWPのKernelが動いておらず`wp tmswp migrate`が登録されないため、fixtureのテーマとプラグインを`--require=tests/fixtures/_wp-cli.php`で読み込んで実行した(`composer discover:check`と同じ方法)。対象はfixtureの2つのModel(テーマの`Contact`のテーブル`tmswp_fixture_contacts`、プラグインの`SpiedModel`のテーブル`tmswp_fixture_spied`)である。

実行したのは最初の確認(`6b47441`)のときである。追加のタスク(`4a0a658`)は`toSql()`の索引の行の順を変えたが、`Contact`はUNIQUEをKEYより先に宣言し、`SpiedModel`は主キーだけのため、この2つのテーブルの`toSql()`とハッシュは変わらない。`MigrateCommand`も変わっていない。

実行のコマンドは、次の形で引数だけを変えた。

```
node node_modules/@wordpress/env/bin/wp-env run cli --env-cwd=wp-content/plugins/tmswp \
  wp --require=tests/fixtures/_wp-cli.php tmswp migrate <引数>
```

実行の前の開発用サイトには、`wp_tmswp_`で始まるテーブルと`tmswp_schema_hashes`のoptionが無かった。実行の順と出力(wp-envの進行の表示を除く)、終了コードは次のとおり。

```
$ wp tmswp migrate --dry-run

tmswp_fixture_contacts: changed

$ wp tmswp migrate

Migrated: tmswp_fixture_contacts

Skipped: tmswp_fixture_contacts (up to date)
```

- `--dry-run`は、定義のハッシュが保存済みと違うテーブルを`changed`として出し、DBを変えない(次の実行でもテーブルが作られた)。

- 否定のフラグ(`--no-force`・`--no-dry-run`)は、指定なしと同じに扱われる。値を付けたフラグ(`--force=0`・`--force=1`・`--dry-run=yes`)と、`--force`と`--dry-run`の併用は、エラーで終了コード1になる。

実行の後に、作られた2つのテーブル(`wp_tmswp_fixture_contacts`・`wp_tmswp_fixture_spied`)を削除し、`tmswp_schema_hashes`のoptionを削除した。開発用サイトのテーブルの一覧は実行の前と一致する。`wp_options`の全行(名前・autoload・値のMD5)を実行の前と比べると、違うのはWP-Cronのロックの`_transient_doing_cron`の値(時刻)だけである。これは実行の前からあるoptionで、WP-Cronを起動するたびに書き換わるため、戻していない。`wp_user_roles`と`_site_transient_theme_roots`は変わっていない。
