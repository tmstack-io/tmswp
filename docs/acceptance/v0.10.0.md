### 5.5 報告の後に決めた事項

T1の報告で挙げた設計の不足6点を、次のとおり決め、docs/06・docs/01に反映した。

1. グループの子(`where(Closure)`)で`lock()`を呼んだら、where系以外を呼んだときと同じく拒否する(docs/06 §4)。
2. `COMMIT`が失敗したら、`ROLLBACK`を試みてから、`COMMIT`の失敗を`QueryException`(番号に応じて専用の例外)で投げる。`ROLLBACK`の失敗より`COMMIT`の失敗を優先する(docs/06 §1)。
3. DBの通常の列をVIRTUALの生成カラムにする場合は、確かめていないまま残し、T3で実測して反映する(docs/06 §5)。T3の実測では、`MODIFY`でできず、MariaDBは1907、MySQLは3106で失敗した。Migratorは、この失敗を`MigrationException`にし、手動の`DROP COLUMN`と`ADD COLUMN`を案内する(7.2)。
4. 起動時にDBの版は検査しない。DBの版はKernelの起動を止める理由にならず、必要な機能が使えなければそのクエリのエラーで止まる(docs/01 §5.5)。
5. `Extra`の実測の読み方はそのままとし、T3の統合テストで全DBのセルについて確かめる(docs/06 R6)。T3の統合テストで、全DBのセルについて、読み方どおりであることを確かめた(7.2)。
6. 手順5aの`SHOW FULL COLUMNS`は、定義に生成カラムがあるときだけ実行する(docs/06 §5)。

あわせて、AGENTS.mdの開発ルールの対応範囲(とdocs/11 §4の写し)にDBの範囲を足し、`IdentifierReservedWordIntegrationTest`・`MigratorColumnTypeIntegrationTest`のコメントのCIのジョブにMariaDB 10.11を足した。

### 5.6 レビューの指摘への対応

別のエージェントのレビューの指摘12件(medium 2、low 10)のうち、1〜11と、12の小項目(1)〜(3)を、次のとおり直した。12の小項目のうち、(4)対象ファイル領域の外の統合テスト2件のコメントの変更(コメントだけで、5.5に記録済み)と、(5)ブランチ保護の必須のチェックへの新しいセルの追加(リポジトリの設定で、ファイルの変更ではない)は、対応しないと決めた。

- wp-env 12は、`.wp-env.json`の`mariadbVersion`か環境変数`WP_ENV_MARIADB_VERSION`でMariaDBの版を変えられる(`node_modules/@wordpress/env/README.md`と`lib/config/db-env.js`の`getMariaDBImage()`で確かめた)。qa.ymlのコメントとdocs/10の4.11・5.1の「固定」の記述を、「既定は`mariadb:lts`で、版は変えられるが、MySQLのセルと同じ方式にそろえるためservicesで立てる」に改めた。方式は変えていない。
- docs/06: 手順7aが使う`TableDefinition::columnSql()`を足した。ほかに次を書いた。
  - transaction()の制御の文をprivateの経路で出すことと、finallyの範囲。
  - execute()の制限の判定の正規表現。
  - rawColumnが生成カラムの構文を判定する正規表現と、それが破壊的変更であること。
  - primary()に生成カラムを含めたときの例外。
  - generated()の型の大文字の拒否。
  - R4の用途。
  - R6の注。

## 6. トランザクションと行ロックの句(T2)

### 6.1 変更の内容

- `Connection::transaction(callable $callback, ?int $lockWaitTimeout = null)`と`inTransaction()`を足した(docs/06 §1)。
  - コールバックが例外を投げれば`ROLLBACK`し、同じ例外を投げる。正常に終われば`COMMIT`し、戻り値を返す。
  - 入れ子と、範囲(1〜1073741824)の外の秒数は、`InvalidQueryException`にする。SAVEPOINTによる入れ子は作らない。
  - `$lockWaitTimeout`を渡すと、この間だけ`innodb_lock_wait_timeout`を変え、終わった後に元の値に戻す。`COMMIT`の後に戻せなければ`QueryException`にする(コミット済みのため、やり直さない)。
  - `ROLLBACK`と秒数の復元で2つ目の失敗が起きた場合は、それを捨て、先の失敗を投げる。
  - 実行中かどうかは、wpdbごとに`WeakMap`で持つ。wpdbの接続をそのまま使い、別の接続は作らない。
  - 自動の再試行はしない。
- トランザクションの実行中に、wpdbの接続のオブジェクトが替わったこと(再接続か、接続を文ごとに切り替えるdb.phpのドロップイン)を、各文の後と`COMMIT`の前に検出し、`COMMIT`せずに`QueryException`を投げる。
- トランザクションの実行中の`execute()`は、トランザクションを終える文と状態を変える文(`START`・`BEGIN`・`COMMIT`・`ROLLBACK`・`SAVEPOINT`・`SET autocommit`・`LOCK`/`UNLOCK TABLE(S)`・DDL・`OPTIMIZE`・`ANALYZE TABLE`・`REPAIR`・`CHECK TABLE`・`FLUSH`・`GRANT`・`REVOKE`)を`InvalidQueryException`で拒否する。
- `QueryBuilder::lock(RowLock $lock)`とenumの`RowLock`を足した(docs/06 §4)。句は`FOR UPDATE`・`FOR UPDATE NOWAIT`・`FOR UPDATE SKIP LOCKED`・`LOCK IN SHARE MODE`の4つで、OFFSETの後に付く。共有ロックは、MariaDBで構文の誤りになる`FOR SHARE`を出さない。トランザクションの外での実行と、`count()`・`update()`・`delete()`・whereのグループとの併用は、`InvalidQueryException`にする。
- `QueryException`のfinalの派生として、`DeadlockException`(1213)と`LockWaitTimeoutException`(1205と、MySQLの`NOWAIT`でロックを得られない3572)を足した。エラー番号は、wpdbの`$dbh`をリフレクションで読み、`mysqli_errno()`で得る(wpdbはエラー番号を公開しないため。docs/06 R6)。
- tmswp/testingの`WpdbTestDouble`が、`START TRANSACTION`・`COMMIT`・`ROLLBACK`・`SET SESSION innodb_lock_wait_timeout = N`を受け付け、トランザクションの状態とロック待ちの秒数を持つようにした。受け付けない文の例外のメッセージの、受け付ける文の一覧も改めた。
- packages/core/rules/model.mdに「トランザクションと行ロック」の節(在庫の引き当ての完全な実装例、`transaction()`・`lock()`の使い方、注意の7つ(1205・1213・オブジェクトキャッシュ・コールバックの中の`exit`等・再接続・db.phpのドロップイン・`WP_DEBUG_DISPLAY`))と、`WpdbTestDouble`でのテストの例を足した。rules/testing.md・README.md・docs/10・CHANGELOGにも書いた。
- 影響範囲: 既存のAPIは変えていない。`WpdbTestDouble`の、受け付けない文の例外のメッセージが変わった。

## 7. 生成カラムと`ON UPDATE CURRENT_TIMESTAMP`(T3)

### 7.1 変更の内容

- `TableDefinition::generated(string $name, string $type, string $expression, GeneratedColumnStorage $storage)`とenumの`GeneratedColumnStorage`(`Stored`・`Virtual`)を足した(docs/06 §2)。
  - 列の行は`{name} {type} AS ({expression}) STORED|VIRTUAL`で、常にNULLを許す(MariaDBは生成カラムの`NOT NULL`を構文の誤りにするため)。
  - 型は、小文字の表記と、`rawColumn()`と同じ型の規則で検証する。式は、字句の6項目で検証し、文字列のリテラルを許したうえで、文の連結等でDDLを壊せないようにする。
  - 生成カラムの後の通常の列と、主キーの生成カラムは、`SchemaException`にする。
- `datetime()`に`onUpdateCurrentTimestamp`を足した。列の行は`rawColumn()`の同じ定義と同じで、ハッシュは変わらない。`rawColumn()`も、定義の最後の日時の関数(`CURRENT_TIMESTAMP`・`NOW(…)`・`LOCALTIMESTAMP`・`LOCALTIME`)の`ON UPDATE`を属性として読む。
- 読み出しの`columnSql()`・`columnOnUpdate()`・`columnGeneration()`・`generatedColumns()`を足した。
- `rawColumn()`が、コメント(`/*`・`*/`・`#`・`--`)と生成カラムの構文(`AS (`・`GENERATED ALWAYS`)を`SchemaException`にするようにした。破壊的変更で、CHANGELOGの「変更」に利用側の直し方とともに書いた。
- 生成カラムへの書き込みを、DBに送る前に`InvalidQueryException`にする。対象は、`Model::insert()`と、`Model::query()`が定義を渡した`QueryBuilder::update()`(`Model::update()`を含む)である。列名の大小文字は区別しない。`QueryBuilder`のコンストラクタに4つ目の引数(`?TableDefinition`)を足した。
- Migratorは、dbDeltaの前からあった生成カラムに、dbDeltaの後で`ALTER TABLE … MODIFY COLUMN`を実行する(dbDeltaは既にある生成カラムの式を変えないため)。式の変更は定義のハッシュで検出し、DBが正規化して保存した式とは表記で比べない。`MODIFY`の失敗は`MigrationException`にし、STOREDとVIRTUALの入れ替え・通常の列からVIRTUALへの変更・UNIQUEの重複の直し方を案内する(docs/06 §5)。
- 適用の後の検証3は、`SHOW FULL COLUMNS`の`Extra`(必須にした)から、生成カラムの保存の方式とON UPDATEを読み、定義と比べる。
- 既定値とON UPDATEの比較で、`NOW(…)`・`LOCALTIMESTAMP`・`LOCALTIME`を`CURRENT_TIMESTAMP`と同じとみなすようにした。`rawColumn()`の`DEFAULT NOW()`等が、既定値の食い違いとして誤って`MigrationException`になっていた不具合の修正で、CHANGELOGの「修正」に書いた。
- packages/core/rules/model.mdに「生成カラム(generated())」と「ON UPDATE CURRENT_TIMESTAMP」の節を足した。アクティブな行だけで一意にする完全な実装例、式の制約、Modelを通して書くこと、`MODIFY`の時間と失敗、式の変更と索引の追加を2回に分けて適用することを書いた。CHANGELOG・docs/10にも書いた。
- 影響範囲:
  - `rawColumn()`で生成カラムかコメントを書いていた定義は、`SchemaException`になる。
  - 適用の後の照合が、生成カラムとON UPDATEも比べる。定義に無いON UPDATEがDBにある列は、次の適用で止まる。
  - `WpdbTestDouble`でMigratorを動かすテストは、`SHOW FULL COLUMNS`の行に`Extra`が要る。
  - 既存の宣言の`toSql()`とハッシュは変わらない。

## 8. upsert(T4)

### 8.1 変更の内容

- `Connection::upsert(string $table, array $values, array $update)`と`Model::upsert(array $values, array $update)`、更新の方法を表すenumの`UpsertUpdate`(`Replace`・`Increment`)を足した(docs/06 §1・§3)。
  - `INSERT … ON DUPLICATE KEY UPDATE`を、挿入する値を更新の句にもう一度バインドする形(`cnt = cnt + %d`・`note = %s`)で出す。`VALUES(col)`はMySQLで非推奨(警告1287)のため、行の別名(`VALUES (...) AS n`)はMariaDBで構文の誤りのため、使わない。列名はクォートしない。
  - 戻り値は影響行数で、1は挿入、2は更新、0は変化なしを表す。`insertId()`は、挿入なら新しいID、更新なら更新した行のID、変化なしなら0を返す。
  - `$values`のnullは`NULL`と書く。nullの`Replace`は`列 = NULL`にする。
  - 空の`$update`と、`$values`に無い`$update`のキーは、`InvalidQueryException`にする。キーは大小文字を区別して比べる。
- `Model::upsert()`は、`$values`に生成カラムがあれば`InvalidQueryException`にする(T3の書き込みの拒否と共通の検査。列名の大小文字は区別しない)。`Connection::upsert()`は、テーブルの定義を持たないため検査しない。
- `WpdbTestDouble`は、upsertを`INSERT`として受け付ける。影響行数が0なら、`insert_id`を0にする。docblock・rules/testing.md・README.mdに書いた。
- packages/core/rules/model.mdに「upsert」の節を足した。視聴の進捗とAPIの利用回数の集計の完全な実装例、出すSQL、`Increment`の値の型と検証、UNIQUEの索引を1つにすること、AUTO_INCREMENTの値の消費、`WpdbTestDouble`でのテストの例を書いた。docs/06の§1とR6、CHANGELOGにも書いた。
- T3で古くなった翻訳ファイルの参照の行番号を直した(7.4)。
- 影響範囲: 既存のAPIは変えていない。

### 8.2 `Increment`の値の型

`Increment`の値は、`int`か`float`に限る。文字列(数字だけの文字列を含む)・`bool`・`BackedEnum`・`Stringable`・`DateTimeInterface`・nullは、DBに送る前に`InvalidQueryException`にする。wpdbは接続のsql_modeからstrictのモードを外すため(docs/06 R6)、`列 + '文字列'`は警告だけで数値に変わり、黙って誤った値になるからである。`BackedEnum`は値に戻す前の型で判定する。ユニットテスト`ConnectionUpsertTest`と、統合テスト`UpsertIntegrationTest::testNullReplaceSetsNullAndNullIncrementIsRejected`(nullの`Increment`が拒否され、行が変わらない)で確かめた。

### 8.3 AUTO_INCREMENTの値の消費

更新になったupsertも、AUTO_INCREMENTの値を1つ消費する。Aを挿入し、Aをupsertで更新してから、Bを挿入すると、BのIDはAのIDより2大きい。`innodb_autoinc_lock_mode`が1のMariaDBと2のMySQLで同じである。統合テスト`UpsertIntegrationTest::testUpdatingUpsertConsumesAnAutoIncrementValue`が全DBのセルで確かめ、rules/model.mdに、IDが飛ぶことと、IDの連続を前提にしないことを書いた。

- 1の生成カラムへの書き込み: `Model`の`insert()`・`update()`・`upsert()`と`Model::query()`のビルダの`update()`で、DBに送る前に例外にする(7.3)。テーブルの定義を持たない`Connection`の書き込みは検査しない(docs/06 §1)。

- 4の「重複したときに更新する列(式を含む)」: 更新の方法は`UpsertUpdate`の`Replace`(`列 = 値`)と`Increment`(`列 = 列 + 値`)の2つだけで、任意の式は書けない(docs/06 §1)。要望書が挙げた式の例(`count = count + VALUES(count)`相当)は`Increment`で書け、要望書の用途(視聴の進捗、APIの利用回数の集計)は2つの形で足りるためである。任意の式を受け付けるには、raw断片の制約(docs/06 R2のクォート文字・複文の禁止とプレースホルダの数の検査)を更新の句にも広げる設計が要り、docs/12 §1.14の「新機能は、必要になるまで追加しない」により、要る用途が出るまで足さない。ほかの式が要る場合は、`Connection::execute()`でプレースホルダを使って書く。
- 1のテストの定義: 要望の定義は2つの生成カラムがどちらもSTOREDだが、テストでは1つをVIRTUALにして、STOREDとVIRTUALの両方の保存の方式を確かめた(7.3)。
- 2の4(デッドロックとロック待ちの時間切れの専用の例外、再試行は呼び出し側が決める): `DeadlockException`(1213)と`LockWaitTimeoutException`(1205と、MySQLの`NOWAIT`の3572)を足した。FWは自動の再試行をせず、回数を指定した再試行の補助(要望書では任意)も作っていない。rules/model.mdの「トランザクションと行ロック」の注意に、呼び出し側で捕まえて処理する書き方を書いた(6.1。`TransactionIntegrationTest::testDeadlockIsDeadlockException`・`testLockContentionTimesOutInTheGivenSecondsAndRestoresTheTimeout`)。
- 2の5(wpdbの接続をそのまま使う): `Connection::transaction()`はwpdbの接続で`START TRANSACTION`等を実行し、別の接続を作らない。接続が替わった場合(再接続、接続を文ごとに切り替えるdb.phpのドロップイン)は、COMMITせずに`QueryException`にする(6.1。`testReconnectionInsideTransactionIsDetectedWithoutCommit`)。
- 要望書の共通の条件: PHPStan level max(run 41053495853のStatic Analysis)と`WpdbTestDouble`での検証(9.3の3)、MariaDB 10.11での動作(9.3の2)、rules/への追記(9.3の4)を満たす。

6(RESTルートの宣言)と7(PHPセッションの管理)は、docs/12 §3.3の目的のとおり、アプリ側の責務と判断し、FWでは作らなかった。

- RESTルートの宣言: WordPress標準の`register_rest_route()`で、引数のJSON Schemaの検証と権限判定ができる。応答の形とエラーコードは案件ごとの決め事である。書き方の手本は、v0.9.1で足したpackages/core/rules/rest.mdにある。2件目の導入先でも要る場合は、coreではなく拡張のパッケージとして検討する。
- PHPセッションの管理: 認証・会員機能はアプリ側の実装の範囲である(docs/00 §2.2の5)。セッションを開く条件・Cookieの属性・有効期間は、案件の要件で決まる。

## 11. 範囲外として残した事項

v0.10.0のタスクの対象の外にあるか、確かめていないため、残した事項である。

1. **UNIQUEの索引が複数あるテーブルのupsert。** rules/model.mdは、重複の判定に使うUNIQUEの索引を1つにするよう書いている(どの索引で重複したかで更新する行が変わるため)。UNIQUEの索引が2つ以上あるテーブルでのupsertの動作は、実測していない。
2. **MariaDB 12.3を明示して立てるCIのセル。** MariaDB 12.3の違い(`DEFAULT LOCALTIME`を`curtime()`と記録する等。7.2)は、T3の使い捨てのコンテナとユニットテストで確かめた。CIでは、wp-envのMariaDB(`mariadb:lts`)が最新のLTSを使うが、その版はイメージの取得の時点で決まり、ジョブのログに版を出していない。
3. **docs/01 §4.5の表(488行)の古い記述。** `main`の行の「v0.9.0の公開までは`rewrite/v0`→`main`のPR」は、今の運用(docs/12 §3.1)と合わない。v0.9.1から引き継いだ事項(`v0.9.1.md` 11章の3)で、v0.10.0のどのタスクの対象ファイル領域にも入っていないため、直していない(3.2)。
4. **プラグインのスターターの例のテストの限界(`v0.9.0.md` 6章の4)。** docs/12 §3.5で、記録だけにして対応しない事項としている。
