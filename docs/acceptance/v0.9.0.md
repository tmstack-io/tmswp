## 3. 利用者のプロジェクトからの導入確認(T5)

Packagistに公開した`tmswp/*`を、monorepoのpathリポジトリを使わずに、利用者と同じ手順で入れて起動した。

### 3.1 確認の方法と環境

- 取得先: Composerのリポジトリは既定のPackagist(`https://repo.packagist.org`)だけで、pathリポジトリを足していない。`COMPOSER_CACHE_DIR`と`COMPOSER_HOME`をリポジトリの外の一時ディレクトリにし、手元のキャッシュを使っていない。
- 手元: PHP 8.5.10、Composer 2.10.3、Node.js 24.18.0、`@wordpress/env` 12.0.0(ルートの`node_modules`のものをパスで呼んだ)。作ったプロジェクトの`composer qa`のlint・analyse・testは手元のPHP 8.5.10で動く。
- wp-env: リポジトリの外に`tools/lib/isolated-wp-env.sh`の`isolated_wp_env_create_work`で作った一時ディレクトリ(`tmswp-t5-adopt.XXXXXXXX`)に、空のテーマ・スターターから作ったテーマとプラグイン・wp-envの設定ファイル・`WP_ENV_HOME`を置き、`wp-env --config=<設定ファイル>`で起動した。設定は`{"core": null, "phpVersion": "8.3", "port": 8895, "testsEnvironment": false, "themes": [<空のテーマ>, <client-theme>], "plugins": [<shop-tools>], "config": {"WP_DEBUG": true, "SCRIPT_DEBUG": true}}`(パスは絶対パス)。プロジェクト名は`wp-env-tmswp-t5-adopt-wp-env-1531b019`で、起動の前に、同じ名前のDocker composeのプロジェクトと資源(コンテナ・ボリューム・ネットワーク・イメージ)が無いことを確かめた。ルートの環境(ポート8890)とsample-siteの環境(ポート8882)は、起動・停止していない。
- 起動したサイト: WordPress 7.1.4、PHP 8.3.36(cliコンテナの`PHP_VERSION`)、`WP_DEBUG`は真。
- 作ったプロジェクトのcomposerのscriptsが呼ぶ`wp`(`wp tmswp discover`等)は、CIのStarter Projectsのジョブ(`tools/ci/bin/wp`)と同じく、PATHに置いた`wp`がこの環境のcliコンテナのWP-CLIへ引数を渡す。

### 3.4 確認の後の片付け

- 確認の後に、`tools/lib/isolated-wp-env.sh`の`isolated_wp_env_remove`で、プロジェクト名の完全一致で環境を消した。wp-envのcleanupでコンテナ・ボリューム・ネットワークが消え、一時ディレクトリも消えた。イメージ2つ(`<プロジェクト名>-wordpress:latest`・`<プロジェクト名>-cli:latest`)は、この関数をzshで読み込んで呼んだため、イメージの一覧の2行が1つの引数として`docker rmi`に渡って失敗した(関数はbash向けで、zshは引用符の無い変数を単語に分けない)。bashで同じ関数の一覧から、2つを完全な名前で`docker rmi`で消した。最後に`_isolated_wp_env_resources`の出力が空(このプロジェクトの資源が無い)ことを確かめた。
- 開始時と終了時のDockerのコンテナ・ボリューム・ネットワーク・イメージの一覧は一致した。`docker system prune`等の名前を指定しない削除はしていない。
