## 3. 実装内容の要約

- settings-page(T1)
  - SettingsPagesを`ExtensionInterface`の実装にし、`KernelConfig`の`extensions`に`new SettingsPages()`を渡したKernelでだけ有効にした。静的な`SettingsPages::register()`・`isRegistered()`・`registerPage()`・`reset()`を削除した。app/の外のページはコンストラクタに渡し、`admin_menu`(initの後)で`definition()`を評価する。slugの重複は、起動したすべてのKernelをまたいで検出する。
  - `add_submenu_page()`のfalseを、権限が無いため登録しなかった正常な結果として扱う(A6-01)。権限の無いユーザーのページ表示とPOSTは、`wp_die()`の403で拒否する。
  - フォームの外枠(wrap・見出し・通知、`$form->open()`・`_step=submit`の保存ボタン・`$form->close()`)とエラー通知をFWが描画し、`render()`は項目だけを描く(A6-07)。保存後の`wp_safe_redirect()`の直後の`exit`は、D-35の1か所だけである。
  - coreのFormに読み取り専用の`Form::isConfirmEnabled()`を足し、確認画面の有効なフォームを`handle()`の前に`LogicException`にした(4章)。
  - `OptionFormBridge::persist()`は、スキーマの型に変換してから保存し、変換できない値・`$only`の未宣言の名前は`LogicException`にして何も保存しない(A6-12)。`applyDefaults()`は、optionの値をFormの既定値の形(文字列。複数選択は文字列のlist)に変換してから渡す。
  - gettextのソース文字列を英語にし、ja訳を同梱した(A6-13)。`SettingsPage::url()`は生のURLを返す(A6-L11)。内部のログは、登録したKernelのロガーに記録する。
- thumbnail(T2)
  - Thumbnailを`ExtensionInterface`の実装にした。thumbnailを登録できるKernelはサイトに1つで、2つ目は`LogicException`にする(D-50)。`tms_thumb()`・RESTのルート・`wp tmswp thumb`は、登録したKernelのdebug・ロガーと、そのインスタンスの設定に従う。静的な`Thumbnail::register()`・`reset()`・`isRegistered()`・`config()`を削除した。
  - `url()`・`tms_thumb()`は`?string`を返す。画像が無いとき(0・空文字・添付ファイルや実体が無い)はdebugでもnullにする(A6-06)。引数・オプションの誤りはdebugに関係なく例外、実行時の失敗はdebugなら例外、本番ならKernelのロガーに記録してnullを返す。
  - 生成を、一時ファイルへの保存と`rename()`、キー単位の`flock`で行う(A6-05)。拡大要求は元画像の寸法で頭打ちにし、画像エディタが扱えない元画像は失敗の印を残して再生成しない(A6-04)。失敗・劣化・ロックの競合の302は`no-store`にした。
  - RESTが既存のファイルを返すたびにmtimeを更新し、302を短期のキャッシュにし、GCは`--days`より古いファイルだけを消す(D-51、A6-10)。キャッシュのディレクトリに印のファイル`.tmswp-thumb-cache`を置き、GC・`status`はキャッシュ自身が作ったファイルだけを扱う。
  - 署名の対象を`serialize([src, w, h, o])`にし、鍵を`wp_salt('auth')`からHKDFで導出した(A6-L06)。URLの値は`rawurlencode`してから埋め込む(A6-11)。`ThumbnailConfig`の全項目をコンストラクタで検証し、`cacheDirName`を1つの安全な名前に限った。
  - REST APIが使えることを利用条件としてdocs/08とREADMEに書き、`RestRouteCheck`が、訪問者からルートが使えないことを検出して管理者に通知する(D-37、A8-13)。
  - `tms_thumb`を`function_exists`で囲まずに定義し(A6-T6-02)、CLIは`WP_CLI::`で直接呼ぶ。
- ja-toolkit(T3)
  - JaToolkitを`ExtensionInterface`の実装にし、モジュールはインスタンスを可変長引数で渡す。静的な`JaToolkit::enable()`・`isEnabled()`・`reset()`を削除した。検査をすべて済ませてから登録する(A6-L09)。`function_exists`で検査を飛ばす分岐を削除した(A6-T6-01)。
  - 訳の読み込み(init 1)を`register()`で予約し、モジュールが0個の`new JaToolkit()`でも読み込む(A6-03)。KanaTextFieldの違反のメッセージは、新設の`KanaRule`で検証の時点に解決する(A6-15)。
  - JapaneseSlugを、許可リストの投稿タイプだけを対象にし、formatを1回の走査で検査し、最悪の長さが200を超えるformatを例外にし、`wp_unique_post_slug()`で一意性を確かめ直す形にした(A6-16)。
  - 全角・半角のスペースだけの検索語は、`is_search()`のまま0件にする(A6-L02)。KanaRuleの正規表現と正規化を直した(A6-L03)。
- 拡張の登録例とrules(T5)
  - packages/core/rules/extensions.mdの登録例を、`tmswp-kernel.php`の`KernelConfig::theme()`・`plugin()`の`extensions`にインスタンスを渡す形にし、4つの拡張の旧APIの例を削除した。サムネイルの例を許可されたキー(`crop`・`quality`)とnullの分岐に直した(A6-17)。
- `wp tmswp thumb clear`の`--days`の誤りの扱い(追加の修正)
  - `--days`の誤り(0・負・整数でない値・値なし・上限を超える日数・`redirectMaxAge`以下の日数)は、何も消さずに`WP_CLI::error()`で`Error:`を出し、終了コード1で終わる。キャッシュの操作の失敗は、従来どおり例外のまま伝える。
  - synopsisを`[--days=<days>]`から`[--days[=<days>]]`にした。
  - `ThumbCache::maxOlderThanDays()`(`intdiv(PHP_INT_MAX, 86400)`)を足し、CLIと`ThumbCache::clear()`の両方で、上限を超える日数を秒への換算の前に拒否する。
- 拡張パッケージのテスト(T4)
  - docs/08の受け入れ基準(CSRF、権限の拒否、PRG、RESTの実応答、CLI、二重登録、FullwidthSearchNormalizer本体)を、ユニット・統合テストで確かめた(A6-08)。3つのパッケージのtests/に`/tmp`のハードコードは無い(A7-L03)。srcは変えていない。
  - docs/08の受け入れ基準の「共通」の項を、1つのインスタンスを2つのKernelに渡す場合と、同じ種類の拡張を2つのKernelにそれぞれ登録する場合に分けて書き直した。

### 5.2 v0.7.0の受け入れ条件

1. 4つの拡張(acf-bridgeを含む)の起動APIが`KernelConfig`経由の登録に統一され、旧APIが残っていない — **満たす**(examples/sample-siteを除く。sample-siteはv0.8.0-T4に持ち越した。6章)
   - 4つの拡張の入口のクラス(AcfBridge・SettingsPages・Thumbnail・JaToolkit)は、どれも`ExtensionInterface`を実装し、`register(Kernel $kernel)`のインスタンスのメソッドで登録される(`grep -rlE "implements ExtensionInterface" packages/*/src`が、この4ファイルを返す)。

#### RESTの応答(`curl -sS -i`)

署名付きのURLは、`wp eval`で`tms_thumb(291, 100, 100)`を呼んで作った(`http://localhost:8890/wp-json/tmswp/v1/thumb?src=id%3A291&w=100&h=100&o&s=<署名>`)。存在しないsrcの署名付きのURLは、`wp eval`で、`Thumbnail`と同じく`UrlSigner::deriveKey(wp_salt('auth'))`の鍵の`UrlSigner`で署名して、`Thumbnail::url()`と同じ形(値を`rawurlencode`して`add_query_arg()`)で作った。以下、署名の値は`<署名>`に伏せた。応答はステータス行と関係するヘッダとJSONの本文だけを抜き出した。

1. 署名の無い要求(上のURLから`s`を除いた) — 403

   ```
   $ curl -sS -i 'http://localhost:8890/wp-json/tmswp/v1/thumb?src=id%3A291&w=100&h=100&o'
   HTTP/1.1 403 Forbidden
   Content-Type: application/json; charset=UTF-8
   {"code":"tmswp_thumb_unsigned","message":"Unsigned thumbnail request.","data":{"status":403}}
   ```

2. 署名の最後の1文字を変えた要求 — 403

   ```
   HTTP/1.1 403 Forbidden
   {"code":"tmswp_thumb_bad_signature","message":"Bad thumbnail signature.","data":{"status":403}}
   ```

3. 正しく署名した要求(1回目。生成する) — 302

   ```
   HTTP/1.1 302 Found
   Location: http://localhost:8890/wp-content/uploads/tmswp-thumb/c0/c002d6b7cb5b7e563506c7ae0786ea936a9ea732.jpg
   Cache-Control: public, max-age=3600
   ```

   `Cache-Control`は`redirectMaxAge`の既定(3600秒)の`public, max-age=3600`で、長期のimmutableではない(D-51)。2回目の同じ要求も、同じ`Location`と`Cache-Control`の302だった。
4. `Location`の取得 — `HTTP/1.1 200 OK`、`Content-Type: image/jpeg`、421バイト。キャッシュのファイルは100x100のJPEGで、`uploads/tmswp-thumb/`の下に、印のファイル`.tmswp-thumb-cache`、キャッシュのディレクトリとshard(`c0`)の`index.html`、生成したファイルがあった。一時ファイルとロックのファイルは残っていなかった。
5. 存在しない添付ファイル(`src=id:999999`)の署名付きの要求 — 404

   ```
   HTTP/1.1 404 Not Found
   {"code":"tmswp_thumb_not_found","message":"Thumbnail source was not found.","data":{"status":404}}
   ```

6. uploadsの下の存在しないファイルのURL(`src=http://localhost:8890/wp-content/uploads/tmswp-t6-manual/missing.jpg`)の署名付きの要求 — 404(本文は5と同じ)

あわせて、次を確かめた。

- キャッシュのファイルのmtimeを`touch -t 202601010000`で過去にしてから、3の署名付きの要求を送ると、302が返り、mtimeが要求の時刻になった(D-51)。
- 生成の後に`wp eval`で`tms_thumb(291, 100, 100)`を呼ぶと、RESTのURLではなく、キャッシュの静的なURL(3の`Location`と同じ)を返した。`tms_thumb(0, 100, 100)`はnullを返した。
- docs/08の受け入れ基準の検証の手順(`curl -i "$(wp eval 'echo tms_thumb(123, 100, 100);')"` → 302 → 画像の取得)は、添付ファイルのIDを291にして、上記の3と4で行った。

| `wp tmswp thumb clear --days=abc` | 同上 | 1 | 変わらない |
| `wp tmswp thumb clear --days`(値なし) | 同上 | 1 | 変わらない |
| `wp tmswp thumb clear --days=106751991167301`(上限+1) | `Error: wp tmswp thumb clear --days must be at most 106751991167300` | 1 | 変わらない |
| `wp tmswp thumb clear --days=30` | `Success: deleted 1 thumbnail cache file(s)` | 0 | 1件消えた |
| `wp tmswp thumb status` | `files: 1`、`bytes: 371`、`failed: 0` | 0 | — |

- 誤りの入力では、出力は`Error:`の1行だけで、PHPのFatal error・スタックトレース・WordPressの「critical error」の文言は出なかった。上限の106751991167300は、この環境(64ビット)の`ThumbCache::maxOlderThanDays()`(`intdiv(PHP_INT_MAX, 86400)`)の値で、`wp eval`で確かめた。
- `status`は、`index.html`(3つ)と印のファイルを数えず、生成した2つのファイルだけを数えた。
- `clear --days=30`は、41日前の100x100のファイルだけを消し、当日の50x50のファイルと、41日前にしたshardの`index.html`、キャッシュのディレクトリの`index.html`と印のファイルを残した(実行後のファイルの一覧で確かめた)。
- `wp help tmswp thumb clear`のsynopsisは`wp tmswp thumb clear [--days[=<days>]]`だった。

1回目(`fa09802`)では、同じ手順で`status`・`clear --days=30`・`status`が上と同じ結果(`files: 2`→`Success: deleted 1 thumbnail cache file(s)`→`files: 1`)だった。一方、`--days`の0・-1・abcでは、何も消さなかったが、`InvalidArgumentException`が捕捉されずに、WP-CLIの出力にPHPのFatal errorとスタックトレース(コンテナの中のパス)と、WordPressの「There has been a critical error on this website.」が出た(終了コード1)。当時のdocs/08 §1.3・§1.4の仕様(違えば`InvalidArgumentException`)のとおりの動きだったが、指揮者の判断で、coreの`MigrateCommand`と同じ`WP_CLI::error()`に揃える追加の修正を行った。1回目では、値なしの`--days`と上限を超える日数は試していない。

確かめていないこと: `--days`の日数が`redirectMaxAge`以下の場合の`Error:`は、既定の`redirectMaxAge`(3600秒)では正の整数の日数がすべて長くなるため、手作業では確かめていない(ユニットテストで確かめている)。RESTの400(寸法・オプションの誤り)、uploadsの外を指すsrcの404、ロックの競合、画像エディタが扱えない元画像は、手作業では確かめていない(統合テストで確かめている)。
