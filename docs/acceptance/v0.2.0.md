## 1. 版の目的

## 3. 実装内容の要約

- Log・Support・ヘルパ(T2)
  - ログのファイル名に `wp_hash()` 由来の接尾辞を付け(ファイル名の形式ごとに別)、URL から推測できないようにした。既定の出力先を公開領域に置く理由と Apache の前提を `07-support.md` に書いた。
  - 書き込み・ディレクトリ作成・保護ファイルの作成に失敗したら、その行を `error_log` へ出し、初回だけ `wp_trigger_error` で知らせる。ローテーションは `scandir` で文字どおりに列挙し、自分の形式の通常ファイルだけを数える。
  - 例外の previous チェーンを出力し、CR / LF をエスケープして 1 記録を 1 行にした。
  - Html の URL 属性に `esc_url` を適用し、許可されないプロトコルは例外にした。
  - ヘルパの `function_exists` のガードを外し、PHPDoc を付けた。スターターのログ出力先を既定に揃えた。
- 探索コマンドと探索結果ファイル(T1)
  - 実行時のキャッシュ(ComponentCache)を廃止し、探索結果ファイル(`tmswp-discovery.php`)をビルド時に生成してコミットする方式にした。本番(debug=false)は探索結果ファイルだけを読み、無ければ例外にする。app/ の走査は debug のときだけ行う。
  - DiscoveryFile(読み込み・出力・照合・書き込み)と `wp tmswp discover [--check]` を新設した。全 Kernel を走査してから書き込み、`--check` は欠けた・古いファイルをすべて挙げて非 0 で終わる。
  - 探索結果に環境で変わる絶対パス(Kernel のルート・ABSPATH・WP_CONTENT_DIR)が含まれると探索失敗にした。属性の解決中の例外は、クラスとファイルを含む DiscoveryException に包む。
  - `composer discover:build` / `discover:check` を追加し、`composer qa` と CI の `coverage` ジョブで照合する。fixture のテーマ・プラグインの探索結果ファイルを生成してコミットした。
- Label・PHPStan 拡張(T3)
  - `label()` を `label(string $singular, ?string $plural = null)` にした。En では複数形が必須で、Ja では省略すると単数形を使う。LabelGenerator が WordPress 7.0 のコアの全キー(投稿タイプ 36・タクソノミー 32)を出す。
  - MetaSchemaReflector・MetaKeyOwnershipRule・MetaBag の型拡張を ReflectionProvider だけで実装し、解析中に利用者のコードを実行しないようにした。MetaBag の型は `list<T>` を返す。オプションの型の絞り込みを、レシーバの型が 1 つの enum ケースに定まる一般の式に効かせた。
  - 統合テストのメタキーを、文字列からクラス定数に戻した。
- Container・例外階層(T4)
  - `TmswpExceptionInterface` を新設し、全パッケージの例外が実装するようにした。使われていない StorageException と、M1 の残骸の UnsupportedComponentException・UnsupportedComponentInitializer を削除した。
  - `Container::get()` に `@template` と条件付きの戻り値型を付け、呼び出し側の型確認(must resolve to)を全廃した。型の合わない登録は登録の時点で例外にする。
  - `has()` を `get()` と同じ規則でコンストラクタの依存を静的にたどって判定するようにし、factory は実行しない。factory の中の例外を、id を含む ContainerException で包む。
- Kernel の起動とフック呼び出し(T5)
  - フックメソッドを `call_user_func_array` で呼び、数値文字列を `int` 引数に渡すフックが通るようにした。`#[Filter]` は最低 1 個の引数で登録する。探索結果ファイルに Action と Filter の種類を持たせ、schema を 4 にした。
  - フックメソッドの実行時の失敗は、本番では Kernel のロガーに記録してそのメソッドだけスキップし、Filter は元の値を返す。Initializer の失敗と属性を復元できない場合は、設定の誤りとして debug に関係なく例外にした。
  - WordPress 7.0 未満を起動時に例外にした。本番の遅延 boot のキャッチアップを、フックが実際に発火した順に実行する。
  - debug の既定値を `WP_DEBUG` の真偽から取るようにした。有効化と無効化は `rewrite_rules` の削除だけにし、毎リクエストの確認をやめた。`Kernel::reset()` をテスト以外から呼ぶことを禁じる PHPStan ルールを追加した。
- 拡張登録・版照合・ラベル言語の既定(T6)
  - `ExtensionInterface::register(Kernel)` と `KernelConfig` の `extensions` で、拡張を Kernel ごとに登録する(同じ Kernel への二重登録は例外)。
  - `Kernel::VERSION` を、読み込まれた全 vendor の installed.php の tmswp/core のリリース版と照合する。psr/container 2・psr/log 3 と違う宣言を、TMSWP の PSR 実装クラスを読み込む前に検出する。
  - LoggerRegistry を Kernel ごとに持ち、チャネルは `KernelConfig` の `logChannels` で宣言する。`Log::set()`・`Log::setRegistry()` を削除し、静的な `Log::*()`・`tms_log()` は呼び出し元のファイルを含む Kernel に記録する。
  - `KernelConfig` の `labelLanguage` を、定義で言語を明示しないときの既定にした。
- 受け入れテストの網羅(T7)
  - `02-kernel.md` の受け入れ基準の各項目に、主張に反する実装なら失敗するテストを揃えた(5.2 の条件 3 の表)。
  - boot の途中から別の Kernel を boot すると KernelException にした。探索結果ファイルの属性を復元できないときは、作り直しの案内付きの DiscoveryException にした。
  - Kernel・Discovery・Container・DiscoveryFile・KernelConfig に許可したもの以外のグローバル可変状態が無いことを、ソースのトークンの検査で確かめる(KernelGlobalStateTest)。

### 5.2 v0.2.0 の受け入れ条件

テストのクラスは、特記の無いものが packages/core/tests/Unit/(ユニット)と packages/core/tests/Integration/(統合)にある。

1. 本番相当(debug=false)で、探索結果ファイルが無いと起動時にエラーになり、ファイルがあれば走査しない(統合テスト)。探索結果ファイルが最新でないと qa が失敗する — **満たす**
   - KernelBootIntegrationTest::testBootFailsWithoutDiscoveryFileWhenDebugIsDisabled は、探索結果ファイルが無いと boot が DiscoveryException になり、Kernel が登録されないことを確かめる。
   - KernelBootIntegrationTest::testBootUsesDiscoveryFileWithoutScanningWhenDebugIsDisabled は、ファイルにだけ書いたフックが登録され、app/ を走査すれば見つかるクラスのフックは登録されず、そのクラスも読み込まれないことを確かめる。
   - `composer qa` は `composer discover:check` を含み、CI では Coverage ジョブが実行して `Success: discovery files are up to date for 2 kernel(s)` を出した。KernelBootIntegrationTest::testCommittedFixtureDiscoveryFilesMatchTheScan は、コミット済みの探索結果ファイルが走査結果と一致することを 4 セルで確かめる。
   - 手元の wp-env で、fixture のテーマの app/Hook/ に `#[AsHook]` のクラスを 1 つ足し、探索結果ファイルを更新せずに `composer qa` を実行した。lint と analyse の後の `composer discover:check` が `Error: TmswpFixtureTheme: …/tmswp-discovery.php is out of date` を出し、`composer qa` は終了コード 1 で失敗した。足したクラスを消した後は、`composer discover:check` が成功し、`composer discover:build` は `wrote 0 file(s)` だった。
2. テーマとプラグインの 2 つの Kernel が同じサイトで起動でき、TMSWP の版の食い違いを起動時に検出する(統合テスト) — **満たす**
   - KernelBootIntegrationTest::testFixtureKernelsAreBootedInDebugModeByWordPressLoading と testThemeAndPluginKernelsAreIndependent は、WordPress の通常の読み込みで boot した fixture のテーマとプラグインの 2 つの Kernel が `Kernel::all()` に含まれ、Container・探索結果ファイル・components が互いに独立していることを確かめる。testThemeAndPluginKernelsEachRegisterTheSameExtensionClass は、両 Kernel が同じクラスの拡張を登録して共存することを確かめる。
   - KernelBootIntegrationTest::testBootDetectsAnotherVendorBundlingADifferentCoreVersion は、別のプラグインの Composer のオートローダの installed.php に別の版の tmswp/core があると、boot が版と install_path を含む KernelException になることを確かめる。
